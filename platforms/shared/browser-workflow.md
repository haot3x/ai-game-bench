# Existing-profile browser creation reference

This is a sanitized operator procedure used in the remote creator pilots.
Creation was DOM-assisted browser operation with screenshots through Chrome
DevTools tooling, **not pure-vision Computer Use**. The public checkout does not
yet ship an unattended browser creator or a Chrome connection tool.

## Connect and submit

1. Obtain permission for the named platform, one fresh project, account spending,
   attempt/time limits and the exact prompt. Login, CAPTCHA and Chrome's control
   prompt remain human steps. Generation permission is not permission to buy
   credits, publish a game or inspect private APIs.
2. Attach to the owner's explicitly selected Chrome profile. Check Chrome's own
   `chrome://version/` Profile Path and bind its browser context/target; store proof
   privately. A window label, logged-in page or last-used profile is insufficient.
   Never fall back to another profile, copy cookies or inspect unrelated tabs.
3. Open the platform's new-project entrypoint in that context. Record visible
   default mode/model labels and account tier when available. A label such as
   "Max" is not backend-model attestation. Do not change defaults unless the
   comparison policy says to do so.
4. Enter the same prompt and **click the actual Send/Build control**. Capture the
   accepted user message and new project/working state. A filled textbox is not
   a submitted generation. Keep mistaken clicks/setup time separate.

## Observe until final delivery

- Capture visible progress, stage/tool/media labels, errors, clarification and
  final response with UTC timestamps and local evidence hashes. Sampled frames
  are not continuous video; record gaps rather than inventing missing events.
- Apply the same semantic clarification preferences across platforms. Record
  exact questions, answers and rationale. Do not send unsolicited extra prompts
  to a platform that did not ask; do not repair or regenerate in a one-shot run.
- Require a final completion signal, no active generation/Stop state, and an
  identified accessible preview. Intermediate build success is not final delivery.
  A delivered artifact still needs a separate gameplay evaluation.
- Record accepted time, last observation still generating, first observation of
  delivery, and any platform-reported time separately. Polling gives a completion
  interval; it does not reveal exact compute time. Use the run's approved timeout,
  not an unlimited monitor or automatic retry.
- Preserve build failure, timeout, login expiry and browser transport failure as
  distinct outcomes. An inaccessible preview is not automatically a game defect.

## Handoff and evaluate

Capture final playable URL/build identity (if exposed), access requirements,
observation time, viewport/zoom/device scale and the exact visible game surface.
Mark URL artifacts unfrozen unless a permitted byte-for-byte export is verified.
Source export or reverse engineering is **not** required to test the game.

Independent evaluation gets the task and game-only surface, not creation chat,
credits or model labels. Use normal visible keyboard/mouse actions; retain
before/action/after evidence and verify input focus. Never read hidden DOM game
state, source, `srcdoc` content or inject a score to prove gameplay. Record any
remaining branding/blinding limits. Historical profile-specific evaluators are
not migrated here: the public counter verifier cannot score these remote games.

Use [record.example.json](record.example.json) privately. Displayed task credits,
balance changes, package-price valuations, provider estimates and actual payments
are separate observations. Convert with a recorded currency/rate/date and keep
the cost basis; USD alone does not make mixed accounting bases comparable.
Never publish raw chats, profile paths, billing screens or signed URLs.
